# Measurement validity and counting rules

`durationMilliseconds` in legacy `Run` exports is total experiment wall time, from runner entry through child cleanup. It includes process startup, readiness polling, scenario traffic, and orchestration. It must not be compared with normal request latency. New run fields are `processStartupMilliseconds` (before `Process.Start` through its return), `applicationReadinessMilliseconds` (before launch through first healthy response), and `scenarioExecutionMilliseconds` (after health through last scenario operation, including restart when requested). The primary future latency metric is scenario execution duration; report startup and total separately. Failed pre-readiness runs have null scenario duration. Existing files retain their original meaning.

Phase 8A.1 adds `llmRequestMilliseconds` and `downstreamOperationMilliseconds`, each the sum of timed calls inside an API execution. A failed attempted call contributes elapsed time; an unattempted category remains null. These are components of scenario execution time, not replacements for it. DirectLlm's `modelToolCalls` records proposals, while its `toolAttempts` records actual executor calls. Proposal and business execution counts must be reported separately across architectures.

`llmRequestCount` counts attempted interpretation calls, including failures. Input/output tokens sum reported provider usage; null is unavailable. A provider response without usage cannot support a zero-token claim. `toolInvocationAttempts` includes `update_booking` argument collection and `create_demo_booking` downstream attempts, so it is **not** a business-operation count. Report the two categories separately in future exports. A duplicate response is not a duplicate committed effect. `committedBusinessEffects` in API metrics is a state projection; `observedBookingRows` is the runner's read-only count from SQLite `bookings`. A successful booking requires exactly one observed row and matching expected API booking fields. Cancellation and denial require zero rows. A missing database or malformed response is unverifiable, never success. For denied create on DirectLlm/WorkflowAgent, the runner sees HTTP 400 but has no execution ID to query; that evidence is narrower. Reconnection currently requires `--restart` to test process recovery; otherwise it is HTTP reconnection only.

The runner stops on missing usage before the next real run. Budget calculation is `(input_tokens × input_USD_per_million + output_tokens × output_USD_per_million) / 1,000,000`. Prices are user supplied. Thresholds checked between runs cannot bound a single run or account for unreported usage/provider-side retries. Provider billing may differ.
